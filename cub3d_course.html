01Overview & program flow

What the program does, and the path it takes from main() to a moving 3D view.

Raycasting is a trick to render a 3D-looking world from a 2D grid map. The world is a simple top-down grid where 1 = wall and 0 = empty. For each vertical column of the screen (800 columns here), we shoot one ray from the player into the grid until it hits a wall, measure the distance, and draw a vertical slice of wall whose height depends on that distance: near walls are tall, far walls are short. That illusion of depth is the whole game.

Key ideaThe map is 2D. The "3D" is faked: we never build a real 3D scene. We just draw 800 vertical strips, one per ray. This is why it's often called 2.5D.

The execution path

main()→ init_data()→ parsing()→ header()→ start_game()→ mlx_loop()
  • argc check: the program needs exactly one argument — the map path (./cub3D maps/valid/easy.cub).
  • ft_calloc: the whole game state lives in one heap struct t_data, zeroed out.
  • init_data: sets every field to a safe default (NULL / 0 / false) — crucial so cleanup never frees garbage.
  • parsing: reads & validates the file. If it returns non-zero, main just returns 0 (the error was already printed and memory freed inside).
  • start_game: opens the window, draws the first frame, registers the hooks, and enters the blocking MLX loop.

This is the parsing pipeline — read it top to bottom: validate the file, copy it into memory, split textures/colors from the map, validate textures & colors, validate the map, then precompute each row's logical length. Every helper returns 1 on failure (a convention used everywhere in the project).

Defense questions
In one sentence, what is raycasting and why is cub3D "2.5D"?
For every screen column we cast one ray across a 2D grid until it hits a wall, then draw a vertical wall slice whose height is inversely proportional to the distance. It's 2.5D because the world data is purely 2D — there's no real 3D geometry, only per-column projection.
Why is the entire state stored in a single t_data allocated with ft_calloc?
A single struct keeps the code clean (one pointer passed everywhere) and calloc zero-initializes it, so every pointer starts NULL. That makes free_data safe to call at any failure point — it never frees uninitialized garbage.
What happens if parsing fails halfway through?
Each step returns 1 on error. The first two steps call ft_error (print + free + exit); the rest return (free_data(data)) which frees everything and returns 1, so main sees a non-zero result and returns 0 without ever opening a window.

02Data structures

Four structs hold the whole program. Know these cold — most defense questions point at a field.

t_player — where the camera is and where it looks

dir vs planedir is the look direction (length 1). plane is perpendicular to dir and controls how wide the field of view is. Together they form the "camera": rays are spread between dir − plane (left edge) and dir + plane (right edge).

t_ray — scratch state for one column's ray

t_texrgbinfo — textures & colors

Watch the index orderThe defines are NORTH 0, SOUTH 1, EAST 2, WEST 3 (cub3d.h l.34-37), and tex[] is filled in that order in prep_game. So tex[2] is EAST, not WEST — a classic off-by-confusion to avoid.

t_data — the master struct

It bundles MLX handles, the file lines, the map grid, the render buffer, and the three structs above. The most important fields for rendering:

Defense questions
Why store pos_x/pos_y as double when x/y are already int?
The grid cell (int) is enough for spawn location, but raycasting and smooth movement need sub-cell precision. pos_x = x + 0.5 puts the player in the center of the cell, and movement adds fractional amounts.
What does the side field mean and why do we need it?
It records whether the ray crossed a vertical grid line (side 0) or a horizontal one (side 1) when it hit the wall. It's used to (a) compute the correct perpendicular distance and (b) pick the right wall texture (N/S vs E/W).
Why does each row need its own length in row_lengths?
Maps aren't required to be rectangular — rows can differ in width and may have trailing spaces. Storing a per-row trimmed length lets bounds checks (check_limit_dda) and collision avoid reading past the end of a short row.

03Parsing the .cub file

Read the file into memory, then split it into "header" (textures + colors) and "map".

The file format

  • NO/SO/WE/EA = wall texture paths (must be .png).
  • F / C = floor / ceiling color as R,G,B (0–255). Spaces around values are tolerated.
  • The map is the last block; 1 = wall, 0 = floor, one of N/S/E/W = player start & facing.

Step 1 — copy the whole file into memory

map_copy_into_file counts the lines first, allocates a char **file array, then reads each line with get_next_line. After this, the program never touches the file descriptor again — everything works on data->file.

Step 2 — separate header from map

extract_data_from_file walks every line. Blank lines are skipped unless the map already started — then anything non-blank after it is an error (the map must be the last block).

The decision "is this a header line or a map line?" is made by is_rgb_or_tex: a line is a header line if it contains any character that is not a valid map character.

Step 3 — store one header line

recognise_texture returns a pointer to the right field (the "slot"). store_texture then refuses unknown identifiers, duplicates, and missing whitespace, and finally fills the slot with either an RGB string or a texture path.

Nice trick: the "slot" pointerBy returning char **slot (the address of the field), the duplicate check is just if (*slot) — if it's already filled, it's a duplicate. One generic function handles all six identifiers.

Step 4 — RGB string → hex color

Colors are validated and packed into a single uint32_t so the renderer can write them directly. The format is 0xRRGGBBFF (FF = fully opaque alpha).

ft_split on ',' must give exactly 3 tokens; each token is checked to be digits-only and within [0,255] by convert_n_check; then the bit-shifts pack them: red into the top byte, then green, then blue, then alpha.

Defense questions
Why copy the whole file into memory instead of parsing it directly from the fd?
It lets the parser look both backwards and forwards freely (e.g. "is everything after the map blank?") without re-seeking the file, and it cleanly separates I/O from logic. The fd is opened, fully read, then closed.
How does the code decide a line belongs to the map vs the header?
is_rgb_or_tex scans the line: if it contains any character outside 01 \t NSEW \r \n, it's a header line (it has letters/digits/paths). Otherwise it's treated as a map line. Once map_started is true, header parsing stops.
Walk me through how "F 135,206,250" becomes a 32-bit color.
get_rgb_value extracts the string "135,206,250"; ft_split by comma gives 3 tokens; each is validated as digits in [0,255]; then (135<<24)|(206<<16)|(250<<8)|0xFF packs them as 0xRRGGBBFF.
What stops "NO file.png garbage" from passing?
get_texture_value reads the path, then skips trailing whitespace; if any non-whitespace remains after the path, it frees the result and returns NULL, which triggers BAD_TEX_VALUE.

04Map validation

Once the map grid is isolated, it must be legal: valid characters, exactly one player, and walls everywhere around the floor.

Valid characters & finding the player

check_cell rejects anything outside 01NSEW. When it meets a direction letter, it records the spawn (orientation + grid x/y), replaces the letter with '0' so the cell becomes walkable floor, and a second player is an error.

Closure — no holes in the surrounding walls

The idea: every walkable cell (0 or where the player stood) must have a wall (or be inside the grid) on all four sides. A space or an out-of-bounds neighbor = a leak to the outside = invalid map.

⚠ Real bug to know for the defenseLook closely at check_closure (l.42-63): when a hole is found it does if (... && check_neighbor(...)) return (0);. Since print_err_msg returns 1, check_neighbor returns 1 on a hole, the condition is true… and the function returns 0 (success). So the error message prints, but the map is not actually rejected — and check_closure always returns 0. An evaluator may push on this. The fix would be return (1); there (or just return (check_neighbor(...)) when it's non-zero).

Player not trapped

check_player_position makes sure the player has at least one floor cell ('0') directly adjacent — otherwise it's boxed in.

Defense questions
Why is the player letter overwritten with '0'?
After the spawn is recorded, the cell is just floor. Replacing N/S/E/W with '0' means the rest of the engine (collision, raycasting, closure) only ever deals with '0' and '1' and never has to special-case the player tile.
How does closure detection work conceptually?
For every walkable cell, check its 4 neighbors. A neighbor that is a space or outside the grid means the floor "leaks" to the exterior — the map isn't sealed. is_open treats out-of-bounds and anything ≤ 32 (space) as open.
(Trap) Is the closure check actually enforced?
No — and that's worth admitting. check_closure returns 0 even when check_neighbor reports a hole, so an open map prints an error but still loads. It should return 1 on a detected hole. (See the bug box above.)
Why reject tabs in the map but allow spaces?
check_elements explicitly errors on '\t' because a tab's visual width is ambiguous and would break the column-based bounds/closure logic; spaces are unambiguous single cells.

05Game preparation

Turn the parsed data into a ready-to-render state: place the camera, build the direction/plane vectors, load PNGs, allocate the pixel buffer.

  • +0.5: centers the player in its grid cell.
  • direction setup: depending on the spawn letter, dir and plane are hard-set (below).
  • mlx_load_png: decodes each wall texture into an mlx_texture_t (raw RGBA pixels).
  • texture_pixels: an 800×800 buffer of uint32_t colors, the canvas raycasting writes into.
Why 0.60?The FOV satisfies FOV = 2·atan(|plane| / |dir|). With |dir| = 1 and |plane| = 0.60, that's 2·atan(0.6) ≈ 61° — close to the classic 60° field of view. Plane is always perpendicular to dir, which keeps the projection undistorted.

Defense questions
Why is the camera plane always perpendicular to the direction vector?
Because the plane represents the projection screen in front of the player. If it weren't perpendicular, the FOV would be skewed and walls would look sheared. Keeping plane ⟂ dir makes the left/right rays symmetric around the view direction.
What sets the field of view, and how would you change it?
The ratio of plane length to dir length. dir is unit length, so the plane length (0.60) alone sets it: FOV = 2·atan(0.6) ≈ 60°. Increase the plane to widen the FOV (more fish-eye-ish), shrink it to zoom in.
What would happen if you forgot the +0.5 offset?
The player would spawn exactly on a grid corner (integer coordinate). That's on a cell boundary and can cause the very first DDA step / collision check to behave oddly. Centering at +0.5 puts the player safely inside a floor cell.

06The core: raycasting + DDA

For each of the 800 columns, build a ray and walk the grid with DDA until it hits a wall.

Building one ray

  • camera_x: maps column x (0..799) to [-1, +1]. Column 0 → −1 (left edge), 400 → 0 (center), 799 → ≈+1 (right edge).
  • ray direction = dir + plane · camera_x. Center column uses pure dir; edges tilt toward dir ± plane.
  • map_x/map_y: the grid cell the player currently stands in (the ray's start cell).
  • deltadist = |1 / ray|: how far along the ray you travel to cross one full cell in X (resp. Y).

Setting the first step

step_x/step_y = which direction the ray walks (+1 or −1). sidedist_x/sidedist_y = the distance from the player to the first vertical / horizontal grid line in the ray's path.

Walking the grid (DDA)

The whole DDA in one sentenceAlways advance toward whichever grid line is closer (smaller sidedist), move into that cell, mark which side you crossed, then check: out of bounds → stop; cell > '0' → it's a wall, done. This jumps grid-line to grid-line, so it only tests cells the ray actually crosses — very fast.

Defense questions
Why DDA instead of stepping the ray by tiny fixed increments?
Tiny fixed steps can skip thin walls or waste cycles inside a cell. DDA jumps directly from one grid line to the next, testing every crossed cell exactly once. It's exact (no missed walls) and as fast as the number of cells crossed.
What exactly is deltadist_x?
The distance traveled along the ray for the ray to move exactly one cell in the X direction. It's |1/ray_x| — derived from similar triangles. Same idea for Y.
Why is the wall test map[..][..] > '0' and not == '1'?
Any character greater than '0' (so '1' and beyond) counts as a wall. After validation the map only holds '0' and '1', so in practice it means "is this a wall." Using > '0' is just a permissive way to say "not floor."
How does the loop avoid reading outside the map?
check_limit_dda verifies map_y is within row_count and map_x within that row's length before the cell is dereferenced; if not, it breaks out of the DDA.

07From distance to a wall on screen

Convert the hit into a perpendicular distance (no fish-eye), then into a slice height and screen position.

Perpendicular distance — the fish-eye fix

We use sidedist − deltadist, which is the distance measured perpendicular to the camera plane, not the straight-line (Euclidean) distance from the eye. If we used Euclidean distance, walls would bulge outward at the screen edges (fish-eye), because edge rays are longer than center rays even for a flat wall. The perpendicular distance cancels that out.

Interactive · why we need perpendicular distance

A flat wall straight ahead. With the fix off (Euclidean), the wall curves; with it on, it stays flat — exactly what the real code does.

Slice height & vertical placement

  • line_height = WIN_HEIGHT / distwall — closer wall ⇒ taller slice. The 0.0001 clamp avoids divide-by-zero.
  • draw_start / draw_end center the slice on the horizon (WIN_HEIGHT / 2) and clamp to the screen, so a huge near wall is simply cropped.
  • pos_on_wall — the exact hit point along the wall, then − floor() keeps only the fractional part (0..1): "how far across this wall tile did we hit?" This drives the texture X coordinate (next chapter).
Defense questions
What is the fish-eye effect and how is it removed here?
Edge rays travel farther than center rays for the same flat wall, so using raw (Euclidean) distance makes walls bulge. Using the distance perpendicular to the camera plane (sidedist − deltadist) makes a flat wall render flat. Try the toggle above.
Why line_height = WIN_HEIGHT / distwall?
It's the projection: apparent size is inversely proportional to distance. A wall one unit away fills (about) the whole screen; twice as far ⇒ half the height. WIN_HEIGHT is the projection scale.
What is pos_on_wall and why subtract floor()?
It's the world coordinate of the hit along the wall. Subtracting its integer part leaves a 0..1 fraction — the position across a single wall tile — which becomes the texture's X column.
Why clamp draw_start/draw_end to the screen?
A very close wall produces a line_height bigger than the window; without clamping, the loop would write outside the buffer. Clamping crops the slice to visible rows only.

08Texture mapping

Pick the right wall image, find the correct texture column, then march down it pixel by pixel.

Which face did we hit?

If the ray crossed a vertical grid line (side 0) it hit an East/West face — and the sign of ray_x says which. Side 1 ⇒ North/South based on ray_y.

Drawing the textured slice

  • line.x = pos_on_wall · texture_width — the texture column to sample.
  • The flip mirrors the texture for two of the four faces so the image isn't reversed depending on which way the ray came.
  • line.step = tex_height / line_height — how many texture rows to advance per screen row. Tall slice ⇒ small step (texture stretched); short slice ⇒ big step (squished).
  • line.pos is the starting texture row, offset so the texture stays centered even when the slice is cropped at the top.
  • & (tex_height − 1) wraps the row index cheaply — works because textures are power-of-two sized.

Reading one texture pixel

MLX42 stores textures as a flat RGBA byte array, row by row. Pixel (x,y) starts at byte (width·y + x)·4. The four bytes (R,G,B,A) are packed into one uint32_t the renderer can store directly.

Interactive · texture column sampling & vertical step

Left: the source texture; the highlighted column is the one chosen by pos_on_wall. Right: that column stretched to line_height using step = tex_height/line_height.

Defense questions
How is the texture column (X) chosen?
pos_on_wall (0..1, where the ray hit across the tile) times the texture width gives the column. A conditional flip mirrors it for the faces where the ray direction would otherwise reverse the image.
What is line.step and why is it a double?
It's how much texture-Y to advance per screen-Y: tex_height / line_height. It's fractional (e.g. 0.32) because the wall slice rarely matches the texture height exactly — a double keeps the sampling smooth and avoids drift.
Why & (tex_height - 1) instead of a modulo?
For power-of-two sizes, x & (n-1) equals x % n but is a single fast bitwise op and safely wraps the index so it never reads out of the texture.
Why pack RGBA into a uint32_t with those shifts?
The render buffer and mlx_put_pixel expect one 32-bit color per pixel (0xRRGGBBAA). Shifting each byte into place builds that single value from the four texture bytes.

09Floor, ceiling & pushing the frame

The main loop fills each column: ceiling above the wall, textured wall, floor below — then blits the whole buffer to the window.

Per column: from the top to draw_start = ceiling color; from draw_end to the bottom = floor color; the middle = textured wall. Floor and ceiling are flat colors (no texture).

Blitting to the window

draw_game = render into the buffer, then copy all 640,000 pixels into the MLX image with mlx_put_pixel. MLX42 displays the image automatically each loop tick.

Note the axis orderThe buffer is indexed texture_pixels[x][y] (column-major), while mlx_put_pixel takes (x, y). Keep that order straight — it's an easy place to introduce a transposed-image bug.
Defense questions
Why render to your own buffer first instead of calling mlx_put_pixel during raycasting?
It separates "compute the frame" from "show the frame," makes the wall/floor/ceiling fill order simple per column, and means you build one complete frame then blit it once — no half-drawn frames.
Are the floor and ceiling textured?
No. They're solid colors (hex_floor, hex_ceiling) parsed from the F/C lines. Only walls are textured. (Textured floor/ceiling would be a bonus feature.)
How many pixels are pushed per frame, and is that a concern?
800×800 = 640,000 mlx_put_pixel calls. It's fine here because frames are only redrawn on input (needs_redraw), not continuously.

keydata.action == 1 means "key pressed" (vs released/repeat). Every handled key sets needs_redraw = true.

Moving with collision (wall sliding)

Why X and Y are validated separatelyBy checking the new X with the old Y, and the new Y with the old X, the player slides along a wall instead of stopping dead: if X is blocked but Y is free, you still move in Y. That's the classic FPS wall-slide.
About MOVE_SPEED = 1One whole cell per key press is a large step — collision only checks the destination cell, not the path, so high speeds could in theory tunnel through a thin wall. For this grid it's acceptable, but it's a fair point to raise in defense.

Rotation — a 2D rotation matrix

The rotation matrixx' = x·cos θ − y·sin θ and y' = x·sin θ + y·cos θ. Both dir and plane are rotated by the same angle so they stay perpendicular and the FOV is preserved. Note olddir_x is saved first because dir_x is overwritten before it's used in the dir_y line.

The frame loop

Registered with mlx_loop_hook, this runs every tick but only re-renders when needs_redraw is set — so a still scene costs almost nothing.

Defense questions
Why move forward with dir but strafe with plane?
dir points where you look, so forward/back follow it. plane is perpendicular to dir, i.e. exactly "sideways," so adding/subtracting it strafes left/right.
Explain the wall-sliding collision.
validate_move tests the new X against the current Y, and the new Y against the current X, independently. If only one axis is blocked, the other still updates — so you slide along the wall instead of stopping.
Why save olddir_x before rotating?
Because the new dir_x is computed and stored first, but the formula for the new dir_y still needs the original dir_x. Saving it prevents using the already-overwritten value.
Why gate rendering behind needs_redraw?
Nothing changes between key events, so re-rendering 640k pixels every tick would waste CPU. The flag means we only redraw right after the player actually moves or turns.

11Memory management & MLX42 lifecycle

One cleanup function frees everything, with guards so MLX teardown never runs twice (the source of the earlier segfaults).

The three boolean guardsdelete, close, terminate ensure each MLX teardown happens at most once. Cleanup can be triggered from several places (parse failure, ESC, window close, normal exit), so without the guards you'd risk a double mlx_terminate → crash. Order matters: delete image → close window → terminate context.

free_data always returns 1 — that's deliberate, so parsing can write return (free_data(data)); and propagate "failure" in one line.

What the "fix segfault" commit changedThe texture array is freed with a fixed bound while (++i < 4) and a NULL check, instead of looping until a NULL terminator that may not exist. Also note free_map does data->path = NULL; without freeing — because path points at argv[1], which you must never free.

MLX42 is the modern MiniLibX rewrite (OpenGL + GLFW, cross-platform). Lifecycle used here: mlx_init → mlx_new_image → mlx_image_to_window → register hooks → mlx_loop (blocks) → on exit, free_data tears it all down.

Defense questions
Why does free_data use boolean flags?
Cleanup can be reached from multiple paths (errors, ESC, window close, end of loop). The delete/close/terminate flags make each MLX teardown idempotent, preventing double-free / double-terminate crashes.
Why is path set to NULL but never freed?
It points to argv[1], owned by the OS, not heap-allocated by us. Freeing it would be undefined behavior; we just drop the pointer.
Why does free_data return 1?
So callers can do return (free_data(data)); to both clean up and signal failure in a single statement, matching the "1 = failure" convention.
In what order must MLX resources be released, and why?
Image first, then window, then terminate the context. The image belongs to the context/window, so destroying the context before the image it owns can crash or leak.

12Makefile & building

How the three pieces — your code, libft, and MLX42 — are compiled and linked.

  • Flags: -Wall -Wextra -Werror (42 mandatory) plus -g for debugging.
  • MLX42 is built with CMake (it's a CMake project, unlike old MiniLibX), producing libmlx42.a.
  • libft is built with its own make.
  • Link line: your objects + libmlx42.a + libft.a, plus -pthread (MLX42 threads), -lm (sin/cos/fabs/floor), and -lglfw (windowing backend).
  • make leaks: runs valgrind with mlx.supp to hide known GPU/driver leaks and focus on your code.
Run itmake then ./cub3D maps/valid/easy.cub. Move with WASD, turn with ← →, quit with ESC.
Defense questions
Why do you link -lm and -lglfw?
-lm provides the math functions (sin, cos, fabs, floor) used in rotation and projection. -lglfw is the window/input backend MLX42 sits on top of; -pthread covers its threading.
How is MLX42 different from the old MiniLibX, build-wise?
MLX42 is a modern OpenGL/GLFW rewrite and ships as a CMake project, so the Makefile invokes cmake to produce libmlx42.a rather than a plain make.
What is mlx.supp for?
A valgrind suppression file that silences leaks coming from the graphics stack (GLFW/OpenGL/drivers) which aren't yours, so make leaks reports only leaks in the project's own code.
